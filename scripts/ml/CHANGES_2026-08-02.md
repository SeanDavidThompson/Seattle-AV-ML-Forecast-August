## QA checklist — run in this order

Each step is separately revertible. A and B are the ones that matter before
Monday.

**Step A — classification only (no model impact)**

1. `reclassify_com_other = TRUE`, `panel_replicate = TRUE`; stop after Step 2c.
   Capture the subgroup counts line and the "Pass 3 reclassified N parcels"
   message.
2. Diff against the current split. Expected direction: `com_other` shrinks,
   `office` loses its vacant-land parcels, `hospitality` gains restaurants.
3. Run `validate_com_class(panel_tbl_com[, .(parcel_id, com_subgroup)])` on
   parcels already assigned by `spec_area_name`. Read the per-tier accuracy
   table. **If tier 4 accuracy is under ~80%, set `com_class_max_tier = 3L`** —
   tiers 1–3 are deterministic and carry no free-text risk.
4. Join `com_class_map` to 2026 AV. Parcel counts overstate the importance of
   small parcels; dollars are the number to report.

**Step B — residual growth (clean A/B)**

5. Run with `com_other_growth_method = "flat"` first. You should reproduce
   today's numbers exactly. If not, stop — something else moved.
6. Switch to `"com_weighted"`. Check `com_other_audit` and the certified
   totals. Watch for `flat_fallback` rows: they mean a year has no subgroup
   growth to average, and the residual silently held flat for it.
7. `"blend"` only after that, if you still want it. Note there is no restaurant
   subgroup — your 30/30/30/10 maps to
   `list(office=.3, retail=.3, hospitality=.3, industrial=.1)`, and
   `hospitality` is hotel-dominated.

**Step C — new features (needs a retrain; do last)**

8. `model_replicate = TRUE`. Cached artifacts are stale — without this the new
   features never enter the models and you get identical numbers, the same trap
   as the first three weighted runs.
9. Compare CV RMSE against current (office impr_delta 0.1103, apt impr_delta
   0.1686). Any target that gets *worse* means the new features are noise for
   that subgroup — drop them there rather than accepting a global regression.
10. Check `con_sales_*` gain share. High placement in the office or industrial
    improvement models is the scenario-varying signal doing its job.
11. Re-run all three scenarios and confirm pess < base < opt on total AV.

## Still unverified

The five new scripts have never touched real data — I have the dictionary and
`EXTR_LookUp.csv`, not the extracts.

- Column names come from the record descriptions plus `janitor::clean_names()`
  conventions in your existing importers. `EXTR_PermitDetail` and
  `EXTR_HomeImpApplication` are the likeliest to need a tweak, since no current
  script reads them.
- `classify_use118()`'s range boundaries are inferred from the ordering of type
  118; the named overrides are verified, the ranges are a default. Step A's
  tier-2/3 accuracy numbers will tell you if they hold.
- `PermitType` / `PermitStatus` are free text of unknown vocabulary in your
  extract vintage. The `is_newconst` / `is_open` regexes are guesses — print
  `table(pm$permit_type_u)` once and tighten them.
- **`kcap_*` and `hi_*` behaviour past the forecast boundary is the thing to
  check hardest.** Rolling permit counts should decay to zero as the window
  passes the last observed permit; if the extend panel freezes them instead,
  you have recreated the housing-permits problem — a high-gain feature that is
  constant across the horizon and therefore scenario-invariant. Re-check
  `FCST_DEAD_CS` after the first run for any new column that is populated
  historically and all-`NA` from 2027 on.
