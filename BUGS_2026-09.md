## B1 — Land-only improvement NA **does** reach published totals

**Verdict: yes, totals are wrong.** The residential land-only fix exists but
sits in dead code; the copy that actually produces the cached forecast does
not have it.

### Root cause: the file is pasted twice

`scripts/ml/06_forecast_av_2026_2031_sequential.R` is 1,119 lines containing
the entire script **twice**:

| | copy 1 | copy 2 |
|---|---|---|
| body starts | line 15 | line 596 (`scenario <- get("scenario", ...)`) |
| scenario loop | 279–572 | ~830–1096 |
| land-only gate | **497–525** | **absent** |
| totals computed | 528 | 1065 |
| `saveRDS(panel_out, rds_path)` | 563 | **1100** |
| `assign("panel_tbl_forecasted_res", ...)` | 581 | **1118** |

Nine top-level helper functions are likewise defined twice
(`drop_single_level_dv_vars`, `load_model`, `load_cache_if_missing`,
`latest_model_file`, `predict_in_chunks`, `predict_lgbm_safe`,
`safe_predict_dummyvars`, `impute_for_prediction`, `align_to_train`).

`grep -n "land_only"` returns hits at **497, 499, 504, 506, 512, 514, 519 only** —
all inside copy 1.

### Why that breaks totals

Copy 1, lines 497–525, coalesces improvements to 0 for parcels with land
history and no improvement history, exactly as its own comment at 490–496
describes:

> `land + NA = NA, so the parcel drops out of total_assessed_filled entirely
> rather than carrying its land value. Coalescing to 0 keeps land-only parcels
> in the population at their correct value.`

Copy 2 reaches its totals line with no such gate:

```r
# line 1062-1065  (copy 2 — no land-only handling anywhere above it)
panel_all[idx_yr,
          total_assessed_filled := appr_land_val_filled + appr_imps_val_filled]
```

`appr_imps_val_filled` is still `NA` for those ~5,796 parcels, so
`total_assessed_filled` is `NA`. Copy 2 runs last and overwrites copy 1's
output at lines 1100 and 1118, so **the cached residential forecast is the
ungated one**.

Downstream aggregations that use `na.rm = TRUE` silently understate rather
than propagating `NA`, which is why this has not surfaced as an obvious
failure: the parcels' **land value is dropped from residential totals
entirely**.

Commercial and condo are unaffected — their gate
(`06_..._sequential_comm.R:241-254`, keyed on `appr_imps_val` history) lives in
a file that is not duplicated.

### Confirming on a real run

```r
p <- readRDS(file.path(cache_dir, "panel_tbl_2006_2031_forecasted_baseline_res.rds"))
p[tax_yr == 2027 & is.na(total_assessed_filled), .N]           # expect ~5,796
p[tax_yr == 2027 & is.na(total_assessed_filled), sum(appr_land_val_filled, na.rm = TRUE)] / 1e9
```

The second figure is the AV missing from published residential totals.

### Fix direction (not implemented)

De-duplicate the file — delete lines 574–1119 — after confirming the two
halves are otherwise identical. That restores the gate and removes the
duplicate-definition hazard in one step. A narrower alternative is to port
lines 497–525 into copy 2 before line 1062, but that leaves the underlying
double-paste in place, which is what caused this.

## B2 — `dist_to_*_km`: no creator has ever existed

`dist_to_public_km`, `dist_to_private_km`, `dist_to_lightrail_km` are consumed
in:

- `03_model_land.R:40-41` (optional-numeric loop), `:97` (feature list)
- `03_model_condo_land.R:105`, `03_model_condo_impr.R:134`
- `03_model_comm_land.R:97`, `03_model_comm_impr.R:97`
- `xx_combine_res_comm_panel.R:127`, `xx_combine_res_comm_condo_panel.R:164`
  (res-only column stubs)
- `xx_combine_parcel_history_changes.R` (`dist_cols` guard)

**No commit in the repository's history has ever assigned them.** Searched
every commit for an assignment, not merely a mention:

```
for c in $(git rev-list --all); do
  git grep -l -E 'dist_to_(public|private|lightrail)_km\s*(:=|<-|=[^=])' $c -- '*.R'
done
# -> empty
```

Three files have ever been deleted from `scripts/`
(`area_report_import.R`, `main_ml.R`, `xx_combine_parcel_history_changes.R`),
all subsequently re-added; none assigned these columns in any revision.

**Conclusion: no creator was removed — one was never written.** The columns
are referenced as if a distance-to-amenity join existed upstream. Every
consumer is guarded (`%chin% names(parcel_dt)`, and the `.opt_num` loop at
`03_model_land.R:40`), so the absence has always been silent. The A2 guard
reporting on this branch will now print `dist_cols: carried 0 of 3` with the
missing names.

Either the join needs writing, or the references should be removed.

## B3 — `current_zoning_3` is single-level because the only thing that creates it is a stub

`current_zoning_3` is **never derived from data**. It appears in `attr_map`
(`00_init.R:109`, mapped from attribute `currentzoning`), in model feature
lists, and in column stubs — but the sole assignment anywhere in the tree is
the fallback in `03_model_land.R:30-32`:

```r
if (!"current_zoning_3" %in% names(panel_tbl)) {
  message("  ℹ️  current_zoning_3 missing from panel (extract schema change) — stubbing constant factor")
  panel_tbl$current_zoning_3 <- factor("Unknown")
}
```

`factor("Unknown")` has exactly one level, so it is dropped as zero-variance in
all four residential models. The same stub exists in `03_model_impr.R`.

### Causal chain

1. `01_import_res.R` reads `EXTR_Parcel` but never selects or derives
   `CurrentZoning` into `current_zoning_3`, so `parcel_res_full` lacks it.
2. `xx_combine_parcel_history_changes.R` builds `facet_cols` from
   `attr_map_noupdate$col_name` and filters with
   `%chin% names(parcel_dt)` — which silently drops `current_zoning_3`
   (this is precisely the silent-guard class A2 addresses).
3. The panel therefore lacks the column.
4. `03_model_land.R:30` stubs a one-level constant.
5. The model drops it.

The raw value *is* available: `01_import_comm.R:317-332` reads
`CurrentZoning` from `EXTR_Parcel` for the commercial universe, and
`xx_com_classify.R:273` has a `zoning_classify()` that buckets the raw string.
Nothing equivalent runs on the residential path.

The name suggests the intended value is the first three characters (or the
zone-class prefix) of `CurrentZoning`, e.g. `"NC3P-75 (M)"` → `"NC3"`. That
intent is not written down anywhere, so it should be confirmed before
implementing.

## B4 — Condo delta target is only built inside a repair branch

`03_model_condo_land.R:82-94` constructs the lags and the delta target:

```r
if ("log_appr_land_val" %in% names(panel_condo) &&
    all(is.na(panel_condo$log_appr_land_val))) {
  ...
  setorderv(panel_condo, c("parcel_id", "tax_yr"))
  panel_condo[, log_appr_land_val_lag1 := shift(log_appr_land_val, 1L), by = parcel_id]
  panel_condo[, delta_log_land := log_appr_land_val - log_appr_land_val_lag1]
}
```

The guard is `all(is.na(...))` — the block runs **only when log AV is entirely
missing**. On a normal run, where the panel already carries `log_appr_land_val`,
the whole block including `delta_log_land` is skipped, and the delta model uses
whatever the panel happened to bring from `04_retrofitting_values.R` /
`05_extend_panel_*`. The ordering guarantee (`setorderv` before `shift`) is
likewise only applied inside the repair branch.

`OUTCOME_DELTA <- "delta_log_land"` (line 189). If that column arrives stale,
mostly `NA`, or near-constant — plausible for condo units, which are commonly
revalued uniformly within a complex so year-over-year log differences collapse
to a handful of repeated values — early stopping fires on round 1 and reports
`Best iter: 1`. The level models are unaffected because they target
`log_appr_land_val` directly, which is populated.

A second contributing factor: `make_rolling_year_folds()` (`00_init.R`) sets
each fold's validation set to `which(tax_yr_vec > cutpoint_yr)`, i.e. *all*
later years, with training as the complement. The earliest fold therefore
trains on ~3 years and validates on the rest, which makes an early stop on a
weak-signal target more likely still.

### Checks to run (diagnostic, not a fix)

```r
panel_condo[, .(n = .N,
                na = sum(is.na(delta_log_land)),
                sd = sd(delta_log_land, na.rm = TRUE),
                distinct = uniqueN(round(delta_log_land, 6)))]
is.unsorted(panel_condo[, .(parcel_id, tax_yr)])   # ordering actually applied?
```

Near-zero `sd`, or `distinct` in the low tens, confirms the target is the
problem rather than the CV scheme.

## B5 — Commercial holdout eval: smallest change (proposal only)

`05_eval_holdout_2025.R:458` reads `panel_tbl_retro_com`, which the subgroup
refactor stopped producing. `main_ml.R` now writes one retro panel per
subgroup, `paste0("panel_tbl_retro_", key)` for `key` in `COM_SUBGROUP_KEYS`
(`main_ml.R:840`, `:1695`), cached as `panel_tbl_retro_<key>.rds`. The
`is.null(panel_com)` branch at `:567-569` therefore always fires and the
commercial block is skipped.

**Smallest change:** leave the entire eval body (`:468-566`) untouched and
replace only the panel acquisition at `:458-465` with a loop that binds the six
subgroup panels into the `panel_com` the existing code already expects:

```r
  .keys <- get0("COM_SUBGROUP_KEYS", envir = .GlobalEnv,
                ifnotfound = c("apt","office","industrial",
                               "retail","hospitality","medical"))
  .parts <- list()
  for (.k in .keys) {
    .p <- get0(paste0("panel_tbl_retro_", .k), envir = .GlobalEnv)
    if (is.null(.p)) {
      .f <- file.path(cache_dir, paste0("panel_tbl_retro_", .k, ".rds"))
      if (file.exists(.f)) .p <- readRDS(.f)
    }
    if (!is.null(.p)) {
      .p <- data.table::as.data.table(.p)
      .p[, com_subgroup := .k]
      .parts[[.k]] <- .p
    }
  }
  panel_com <- if (length(.parts))
    data.table::rbindlist(.parts, use.names = TRUE, fill = TRUE) else NULL
  if (!is.null(panel_com))
    message("  Loaded ", length(.parts), " subgroup retro panels for eval: ",
            paste(names(.parts), collapse = ", "))
```

Why this is the minimum:

- The eval body keys on `parcel_id`/`tax_yr` and the model predictors, none of
  which are subgroup-specific, so a row-bind is a drop-in for the old panel.
- `fill = TRUE` tolerates subgroups whose columns differ slightly.
- The existing `is.null(panel_com)` skip still works when no subgroup panel is
  cached, so behaviour is unchanged on a cold cache.
- Carrying `com_subgroup` costs one column and makes per-subgroup metrics
  possible later without another refactor.
